# Замер производительности, 2026-10-04, базовая линия

## Окружение

MacBook Pro (Apple Silicon), API и k6 на хосте, Postgres 16 и MinIO в Docker (OrbStack), сеть
localhost. Данные генератора `backend/cmd/seed` по плану из `docs/testing.md`: 1 000 пользователей,
100 клубов до 150 человек, 200 000 тренировок, 20 000 постов, 5 000 объявлений, 50 000 сообщений,
500 забегов. Коммит бэкенда `859d972` плюс инструменты нагрузки.

Абсолютные значения оптимистичны: нет сетевой задержки, нет TLS, база греется в памяти одной
машины. Для прода ориентир: прибавить 5–20 мс сети на запрос и делить пропускную способность
на разницу в CPU.

Ошибок нет, латентность падает с ростом нагрузки за счёт прогрева кэша Postgres. Предел на этой
машине задаёт сам k6, а не API: достигнуто в среднем 382 RPS при целевых до 1 000. Загрузка CPU
Postgres на ступенях не снималась.

## Выводы

- Горячие запросы ходят по индексам, N+1 и квадратичных мест при объёмах первого года нет.
- Запас по латентности 10–30 раз против порогов; на проде он сожмётся сетью, но останется.
- Слабые места по росту, не по текущим цифрам: опрос диалогов, состояние достижений по всей
  истории спортсмена, проверка бана запросом на каждый вызов, подстрочный поиск по объявлениям,
  фасет брендов полным сканом. Подробности и план в `docs/testing.md`.
- Не измерено: LiveKit как медиасервер (отдельный тест `lk load-test`), клиент на устройстве,
  поведение при 10 000 одновременных клиентов (нужна машина мощнее ноутбука).
