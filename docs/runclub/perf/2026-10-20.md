# Замер производительности, 2026-10-20: пагинация списка диалогов

## Окружение

То же, что в `2026-10-13.md`: MacBook Pro (Apple Silicon), API и k6 на хосте, Postgres 16 в Docker. Данные
`backend/cmd/seed` с `-rng-seed 1` в отдельной базе `runclub_load`, API на `:8081`, Redis DB 1,
`DB_MAX_CONNS=10` (столько же соединений, сколько давал прежний пул по числу ядер). Сценарий `threads.js`, 60 секунд,
20 RPS, продавец с 200 диалогами.

База сравнения — `main` на коммите `55579c7`, до пагинации. Порог по плану: страница из 50 диалогов, p95 ниже базы,
порог 150 мс сохраняется.

## Планы запросов

- Страница списка: `Index Only Scan` по новому `listing_threads_seller_list_idx`, 0.03 мс на ветку продавца.
- `CountUnreadMessages` после удаления одноколоночных индексов ограничен `last_message_at IS NOT NULL` и идёт по
  тем же частичным индексам. Сообщения он по-прежнему читает полным проходом (48 тыс. строк, 8.8 мс): это слабое
  место коррелированных счётчиков из `docs/testing.md`, пагинация его не меняла.

## Бейдж непрочитанных

`CountUnreadMessages` переписан на счёт по каждому диалогу (`LATERAL`): индекс `listing_messages_thread_idx`
отдаёт только сообщения после отметки о прочтении, а прежний общий join планировщик делал полным проходом
`listing_messages`. Новый сценарий `backend/load/unread.js`: продавец с 200 диалогами, 20 RPS, 60 секунд.
База сравнения — `main` на `af5e3b6`.

| Метрика | `main` | Счёт по диалогам | Вердикт |
|---|---|---|---|
| p95 `GET /threads/unread`, мс (порог 50) | 6.37 | 5.77 | PASS |
| Время запроса в `EXPLAIN ANALYZE`, мс | 7.7 | 0.9 | PASS |
| Полный проход `listing_messages` | да, 48 тыс. строк | нет | PASS |
| Счёт | 2021 | 2021 | PASS |

Основная часть оставшихся 5.8 мс приходится на HTTP и авторизацию, а не на базу.

## Пульс при импорте из Здоровья

Вопрос: быстрее ли один запрос пульса за окно пробежек (B), чем отдельный запрос на каждую пробежку (A, текущий
код, запросы параллельно). Замер на iPhone 15 Pro, профильная сборка, временный код, в репозиторий не попал.
В «Здоровье» записаны синтетические данные от имени приложения: 30 пробежек по 45 минут с пульсом раз в 5 секунд
и фоновый пульс раз в 10 минут за 31 день, после замера удалены. Восемь проходов в порядке A, B, B, A, A, B, B, A.

| Вариант | Время, мс | Точек пульса через канал | Расхождение среднего пульса |
|---|---|---|---|
| A, запрос на пробежку | 208–221 | 15 776 | 0 из 29 |
| B, один запрос на окно | 511–532 | 19 696 | 0 из 29 |

Вывод: B медленнее в 2,4 раза. Он тащит через канал платформы ещё и фоновый пульс между пробежками, а разбор
идёт в одном потоке. Текущий вариант A остаётся. Повторять без новых данных не нужно.
