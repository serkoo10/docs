# Стратегия тестирования

Что уже есть, чего не хватает и в каком порядке закрывать. Уровни идут от дешёвых к дорогим,
каждый ловит свой класс ошибок, ни один не заменяет другой.

## Что есть

| Уровень | Где | Что ловит |
|---|---|---|
| Юнит-тесты сервисов Go с фейками хранилища | `backend/internal/*/service_test.go` | Правила домена, права, статусы, границы валидации |
| Интеграционные тесты HTTP на реальном Postgres | `backend/internal/httpserver/integration_*_test.go` | SQL, маппинг ошибок, сквозные сценарии по этапам |
| Юнит-тесты Dart: домен, нотифаеры, интерцепторы | `app/test` | Форматы, пагинация, refresh токенов, права на клиенте |
| Виджет-тесты критичных экранов на фейках `test/support` | `app/test/features/*/*_screen_test.dart`, `workout_card_test.dart` | Вёрстка и реакции: вход с выбором страны, карточка тренировки, композер поста, экран звонка |
| Контракт: эталонные ответы бэкенда, разбор моделями клиента | `docs/fixtures`, `backend/internal/httpserver/integration_fixtures_test.go`, `app/test/contract` | Расхождение ответов бэкенда с моделями клиента: падает на одной из сторон |
| Smoke-тест на iOS-симуляторе и Android-эмуляторе со скриншотами | `app/integration_test`, `app/tool/smoke.sh` | Сборка, навигация, что экраны вообще открываются |
| Проба LiveKit Go-клиентом | `backend/cmd/lkprobe` | Вебхуки, подпись, учёт присутствия |

Эталоны перегенерируются командой `UPDATE_FIXTURES=1 make test` в `backend`; изменённые файлы идут в коммит вместе с правкой API.

Нагрузочные k6-сценарии в `backend/load/` идут по плану измерений ниже. Запускаются руками перед релизом и после
каждого изменения SQL в горячих запросах; отчёты в `docs/perf/`.

## Чего не хватает, по приоритету

1. **Проверка на устройствах.** Матрица: iPhone (iOS 17 и последняя), Android (Pixel и Samsung,
   Android 12 и 15). Сценарии руками: вход через Apple, импорт из Здоровья и Health Connect,
   звонок двух устройств 30 минут в фоне и с блокировкой экрана, загрузка видео 300 МБ по Wi-Fi.
   Это нельзя автоматизировать в симуляторе: ни камеры, ни HealthKit, ни фонового аудио.
2. **Безопасность.** Прогон по чек-листу: IDOR на всех `/{id}` (участник чужого клуба, чужое
   объявление, чужая сессия), перебор OTP с учётом лимитов, подпись вебхука LiveKit, подмена
   `video_url` на внешний хост, размер тела запроса, права админ-токена.
3. **Бета с клубами.** 3–5 клубов до 200 человек в TestFlight, метрики из базы SQL-запросами:
   тренеры с клубом за первую неделю, ученики с первым выполненным заданием, удержание на 4-й неделе.

## План измерений производительности

Правило: измерение запускается только после согласования сценариев, метрик, базы сравнения и
порога. База сравнения для первого прогона: текущий `main`, дальше сравнение с предыдущим прогоном.

Данные для нагрузки: генератор `backend/cmd/seed` создаёт 1 000 пользователей,
100 клубов по 10–150 человек, 200 000 тренировок за год, 20 000 постов, 5 000 объявлений,
50 000 сообщений, 500 забегов. Пропорции взяты из целей первого года.

| Сценарий | Запрос | Метрика | Порог |
|---|---|---|---|
| Лента клуба на 150 человек, 2 000 постов, 30 блокировок у читателя | `GET /clubs/{id}/posts` | p95 латентность при 50 RPS | ≤ 150 мс |
| Неделя тренировок спортсмена при 2 000 его тренировок | `GET /workouts?from&to` + `summary` | p95 | ≤ 100 мс |
| Календарь тренера на клуб 150 человек, неделя | `GET /clubs/{id}/workouts` | p95 | ≤ 200 мс |
| Импорт 100 тренировок пачкой | `POST /workouts/import` | p95, число запросов к базе | ≤ 1 с, ≤ 3 запроса на элемент |
| Выполнение тренировки с оценкой достижений | `POST /workouts/{id}/complete` | p95 | ≤ 120 мс |
| Доска объявлений с фильтром по городу и бренду, 5 000 активных | `GET /listings?...` | p95 при 100 RPS | ≤ 150 мс |
| Первая страница диалогов с непрочитанными (50 из 200 у продавца) | `GET /threads` | p95 | ≤ 150 мс |
| Бейдж непрочитанных у продавца с 200 диалогами | `GET /threads/unread` | p95 | ≤ 50 мс |
| Опрос диалога 1 000 клиентов раз в 10 с | `GET /threads/{id}/messages` | RPS сервера, CPU Postgres | ≤ 30 % CPU одного ядра |
| Календарь забегов на год, 500 стартов, с фильтрами | `GET /races` | p95 | ≤ 150 мс |
| Проверка бана в middleware | любой авторизованный запрос | добавка к латентности | ≤ 2 мс |
| Вебхуки LiveKit: 100 участников входят в минуту | `POST /webhooks/livekit` | p95, пропуски | ≤ 50 мс, 0 пропусков |
| Клиент: лента 500 постов с фото | скролл | кадры дольше 16 мс (jank) по DevTools | ≤ 1 % кадров |
| Клиент: холодный старт | запуск до главного экрана | время на iPhone 12 | ≤ 2 с |

Запуск: `backend/load/run.sh --seed` при API, запущенном с фиксированным `JWT_PRIVATE_KEY`
(подробности в `backend/load/README.md`). Итоговая таблица пишется в `backend/load/results/summary.md`.

Урок первого прогона 2026-10-04: сценарий импорта слал все пачки одному спортсмену и за минуту
раздул его историю до 120 тысяч тренировок, после чего `complete` мерился на искажённых данных и
показал 264 мс, а импорт 2,1 с. После раздачи пачек по разным пользователям и переноса `complete`
перед импортом оба сценария в порогах: 31 мс и 245 мс. Форма нагрузки важна не меньше порога.

После измерения кандидаты на исправление выбираются минимум из двух слоёв: индекс или форма
запроса в SQL, кэш в сервисе, форма ответа или пагинация в API, рендер на клиенте. Решение по
симптому в одном слое не принимается.

## Слабые места по результатам первого замера

Ни одно не проявилось при объёмах первого года, порядок по тому, что сломается первым при росте.

| Место | Почему слабое | Когда проявится | Варианты по слоям |
|---|---|---|---|
| Опрос диалогов раз в 10 с (закрыто: SSE через Redis, опрос раз в 30 с только без потока) | 100 RPS на 1 000 активных клиентов съели 17 % ядра Postgres; растёт линейно с онлайном | 5–10 тыс. одновременных клиентов | Протокол: push через APNs/FCM вместо опроса; транспорт: SSE или WebSocket; клиент: опрос только на открытом экране, уже так |
| Состояние достижений читает всю историю спортсмена (закрыто: генерируемые колонки и покрывающие индексы, index-only) | Два запроса на каждое `done` сканируют и разбирают jsonb по всем тренировкам; на аномалии в 120 тыс. строк дало 2 с | Спортсмены с 10–20 тыс. тренировок | Данные: строка агрегатов на спортсмена, обновляемая в том же выражении, что ставит `done`; SQL: колонки `distance_m`, `duration_s` вместо jsonb плюс покрывающий индекс |
| Проверка бана запросом на каждый вызов (закрыто: кэш 30 с с инвалидацией при бане) | 1,6 мс из 2,2 мс дешёвого эндпоинта это поход в базу | Любая нагрузка на дешёвые эндпоинты | Сервис: кэш на 30–60 с с инвалидацией при бане; протокол: флаг в access-токене и короткий TTL |
| Поиск по объявлениям подстрокой | `position()` по названию, бренду и модели это полный скан активных | 50 тыс. активных объявлений | SQL: `pg_trgm` GIN-индекс; продукт: поиск только по бренду и модели из справочника |
| Фасет брендов | Полный скан активных объявлений на каждый запрос фильтра | Те же 50 тыс. | Сервис: кэш на минуту; данные: счётчики по брендам |
| Коррелированные счётчики `member_count`, `going_count`, `unread_count` (бейдж непрочитанных закрыт: счёт по диалогам через индекс) | Диапазонный скан по размеру клуба, забега или диалога на строку | Клубы в тысячи человек | Данные: денормализованные счётчики; пока не нужно |

Отдельно от API: LiveKit как медиасервер не измерялся. Один узел на 4 ядра держит порядка сотни
участников с видео; это проверяется `lk load-test` на будущем хостинге, не на ноутбуке.
