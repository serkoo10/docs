# StudCore — система учёта контингента и документов для вузов

**Дата:** 2026-09-15
**Статус:** дизайн утверждён, ожидает реализации
**Предшественник:** 1С:АКАДА (конфигурация на платформе «1С:Предприятие 8»)

## 1. Задача

Сотрудники учебной части вуза ведут контингент студентов и выдают по нему документы
(справки об обучении, справки-вызовы, доп. соглашения к договорам) в старой конфигурации
на платформе 1С. Система медленная, интерфейс разнесён по множеству окон, печатные формы
зашиты внутрь конфигурации и меняются только 1С-программистом.

Строим самостоятельный SaaS-продукт для вузов и учебных центров, закрывающий этот участок
работы. Данные из существующих систем переносятся импортом; интеграция с чужой 1С
в периметре заказчика в задачу не входит.

Как эта работа устроена сегодня, по образцу реальной справки: документ
**заполняется вручную в Word**. Сотрудник открывает файл по прошлому студенту,
правит фамилию, дату рождения, курс, реквизиты приказа и сохраняет под новым
именем. Печатная форма 1С при этом существует, но живого документа из неё не
получается — итоговый бланк всё равно доводится руками. Отсюда следует, что
основная потеря времени здесь не в скорости системы, а в ручном труде и в
ошибках, которые он порождает: перенесённый от прошлого студента курс, чужая
дата приказа, несогласованное склонение фамилии.

**Целевая нагрузка:** сотни сотрудников на арендатора, до ~50 запросов в секунду в пике.
Это малая нагрузка; узкое место продукта — не пропускная способность, а отзывчивость
интерфейса и скорость выдачи документа.

## 2. Что входит в первую версию

Контингент и документы:

- карточки студентов с историей изменений;
- договоры на обучение и доп. соглашения к ним;
- шаблоны документов в DOCX, выдача документа с номером, снимком данных и PDF;
- сквозной поиск по студентам;
- импорт данных из Excel/CSV;
- мультиарендность, роли, журнал доступа.

**Явно не входит в первую версию:** приказы и движение контингента, учебный процесс
(планы, ведомости, сессия), финансы и задолженность, личный кабинет студента,
пакетная выдача документов, ЭЦП, синхронизация с 1С через OData.

## 3. Архитектура

**Модульный монолит на Go + PostgreSQL, SPA на React/TypeScript.**

Микросервисы на старте отвергнуты сознательно: при целевой нагрузке они не дают выигрыша,
но втрое удлиняют путь до работающего продукта и превращают транзакцию
«создать доп. соглашение + обновить договор + записать в историю» в распределённую сагу.
Свойства, ради которых их обычно берут (независимое масштабирование, отзывчивость,
изоляция отказов), достигаются здесь схемой БД, фоновым воркером и клиентским кешем.

### Процессы

| Процесс | Назначение |
|---|---|
| `api` | HTTP API, вся доменная логика. Stateless, масштабируется репликами. |
| `worker` | Фоновые задачи: импорт, конвертация. Очередь на PostgreSQL (`river`). |
| `postgres` | Единственное хранилище состояния. |
| `minio` (S3) | Файлы: шаблоны, выданные документы. |
| `gotenberg` | Конвертация DOCX → PDF (изолированный контейнер поверх LibreOffice). |
| `caddy` | TLS-терминация, статика фронтенда. |

### Модули внутри `api`

| Модуль | Владеет таблицами |
|---|---|
| `identity` | users, roles, sessions |
| `tenants` | tenants, settings |
| `students` | persons, enrollments, groups, person_history |
| `contracts` | contracts, contract_amendments |
| `documents` | document_templates, issued_documents, document_numbers |
| `import` | import_jobs, import_staging |

**Правило границ:** модуль обращается к данным другого модуля только через его
Go-интерфейс, никогда напрямую в чужие таблицы. Нарушение ловится тестом на граф импортов.

### Путь к сервисам

Разделение выполняется по триггерам, а не по календарю:

- генерация документов стабильно занимает >20% CPU и влияет на задержки API → выносится `documents`;
- импорт крупного арендатора деградирует отзывчивость → выносится `import`;
- вторая команда разработки, деплои мешают друг другу → разрез по границам модулей.

До наступления триггеров разделение не выполняется.

## 4. Модель данных

### Человек и обучение разделены

`person` — персональные данные (ФИО, дата рождения, документ, контакты).
`enrollment` — факт обучения: программа, форма, курс, группа, статус, даты.

Один человек может иметь несколько обучений (второе высшее, восстановление после
отчисления). Объединение этих сущностей в одну таблицу порождает дубли при
восстановлении и делает историю статусов неразрешимой.

### История ФИО

Изменения полей `person` пишутся в `person_history` с датой. Текущие значения лежат
в `person`. Требуется дважды: документ, выданный до смены фамилии, обязан сохранять
прежнее ФИО, и журналирование изменений ПДн требуется 152-ФЗ.

### Выданный документ неизменяем

`document_template` — DOCX-шаблон арендатора.
`issued_document` — факт выдачи: номер, дата, выдавший сотрудник, **снимок всех
подставленных значений в JSONB**, ссылка на файл в S3.

Документ никогда не перегенерируется из актуальных данных. При необходимости изменений
выдаётся новый документ с новым номером; прежний помечается аннулированным со ссылкой
на замену.

**Нумерация:** последовательность на пару (арендатор, вид документа) с настраиваемым
форматом номера — маска с порядковым номером, годом и кодом подразделения, со сбросом
счётчика по году. Номер выделяется в момент подтверждения выдачи; предпросмотр его
не расходует.

**Пропуски в нумерации допустимы.** В существующей практике вузов они возникают
постоянно: аннулирование, испорченные бланки, выдача вне системы. Требование —
уникальность и монотонность номера, а не сплошной ряд. Это снимает необходимость
сериализовать выдачу документов (иначе два сотрудника не смогли бы выдать справку
одновременно) и позволяет использовать обычную последовательность PostgreSQL.

### Договор и доп. соглашения

`contract` неизменяем после подписания. `contract_amendment` — отдельная запись со
ссылкой на договор и перечнем изменяемых условий (стоимость, срок, программа).
Действующие условия на дату вычисляются как договор плюс применённые к этой дате
соглашения. Это даёт корректный ответ на вопрос «какие условия действовали в прошлом
периоде», недостижимый при правке договора на месте.

### Мультиарендность

`tenant_id` присутствует во всех таблицах предметной области. Изоляция обеспечивается
Row Level Security на уровне PostgreSQL: политика не позволит запросу одного арендатора
получить строки другого даже при отсутствии фильтра в коде. Одна база на всех
арендаторов; крупный арендатор при необходимости выносится в отдельную базу без
изменений в коде.

### Состав обучения

Поля `enrollment` определяются тем, что подставляется в документы: форма обучения,
направление подготовки (код и название, например `44.03.01 «Педагогическое
образование»`), курс, основа обучения (платное или бюджетное, от неё зависит
формулировка о стипендии), дата начала обучения, плановая дата окончания и
**реквизиты приказа о зачислении — номер и дата**.

Приказ о зачислении попадает в справку, поэтому его номер и дата хранятся в
карточке обучения уже в первой версии. Полноценная работа с приказами как с
документами (движение контингента, переводы, отчисления) остаётся за рамками
первой версии — здесь нужны только два поля.

### Реквизиты арендатора

Шапка и подвал документа целиком состоят из реквизитов учебного заведения:
полное наименование, почтовый адрес, телефон, ИНН, номер и дата лицензии на
образовательную деятельность, номер и дата свидетельства об аккредитации,
должность и фамилия подписывающего, изображения подписи и печати. Всё это —
настройки арендатора, а не текст в шаблоне: при смене ректора или продлении
лицензии правится одно поле в настройках, а не десяток шаблонов.

### Удаление

Физическое удаление не применяется. Мягкое удаление с отметкой времени и автора.

## 5. Документы

Онбординг арендатора: заказчик предоставляет образцы своих печатных форм, они
однократно превращаются в DOCX-шаблоны. Продукт поставляется с библиотекой типовых
форм (справка об обучении, справка-вызов, доп. соглашение об изменении стоимости).

Шаблоны редактируются сотрудником арендатора в Word, без участия разработчика —
это ключевое отличие от текущей системы, где форма зашита в конфигурацию.

**Подстановка.** Плейсхолдеры вида `{{ФИО}}`, `{{Группа}}`, `{{ДатаВыдачи}}`.
Word разбивает плейсхолдер на несколько XML-фрагментов (runs) при любом редактировании,
поэтому перед подстановкой выполняется нормализация runs. Это единственная техническая
неизвестность проекта, снимается спайком до начала разработки (см. §9, этап 0).

**Склонение и числительные — обязательная часть подстановки.** Справка начинается
словами «Дана Петровой Анне Сергеевне»: фамилия, имя и отчество стоят в дательном
падеже, причём склоняется здесь не всё — часть фамилий несклоняема. Курс печатается
дважды, цифрой и прописью («3» и «третий»). Дата набрана в русском виде: «15»
сентября 2026 г. Наивная подстановка именительного падежа даёт документ, который
придётся править руками, то есть не решает исходную задачу.

Решение: падежные формы ФИО хранятся в карточке человека. При заведении студента
они заполняются автоматически библиотекой склонения, сотрудник видит результат и
может поправить его один раз — дальше все документы по этому человеку печатаются
правильно. Автоматика при этом не обязана быть безошибочной, и это снимает главный
риск подхода. Числительные прописью и русские форматы дат реализуются функциями
шаблона и отдельного хранения не требуют.

**Конвертация в PDF** выполняется в отдельном контейнере `gotenberg`, не в процессе `api`.

**Проверка подлинности.** На документ наносится QR-код со ссылкой на публичную страницу
проверки, показывающую номер, дату и статус документа без раскрытия персональных данных.

**Подпись и печать** — факсимиле в виде изображения в шаблоне. Квалифицированная ЭЦП
в первую версию не входит.

## 6. Интерфейс

Пользователь — оператор ввода, а не посетитель сайта. Приоритет плотности информации
и работы с клавиатуры над визуальным простором.

**Целевые показатели:** первый результат поиска — до 100 мс; открытие карточки
студента — до 200 мс; готовый документ на экране — до 3 с.

**Поиск — главный экран.** Одна строка ищет одновременно по ФИО, номеру договора,
номеру группы и номеру зачётной книжки, с устойчивостью к опечаткам (`pg_trgm` + GIN).
Подтверждено: типичный сценарий — работа с конкретным студентом, а не со списком группы.

**Карточка студента — один экран** с вкладками: персональные данные, обучение,
договор с доп. соглашениями, выданные документы, история. Открытие дополнительных
окон не требуется.

**Клавиатура.** Командная палитра (`Cmd/Ctrl+K`): переход к студенту, выдача справки,
создание доп. соглашения.

**Стек:** React + TypeScript + Vite, TanStack Query (кеш, фоновое обновление,
оптимистичные обновления), **Ant Design** как библиотека компонентов.
Пагинация курсорная.

Ant Design выбран вместо связки Tailwind + shadcn/ui потому, что продукт по
характеру ближе к ERP, чем к веб-сайту: нужны таблицы с сортировкой, фильтрами
по колонкам и фиксированной шапкой, формы с валидацией, календарь и выпадающие
списки с поиском. Всё это в Ant Design присутствует готовым, включая штатную
локализацию `ru_RU` с русскими форматами дат и текстами компонентов. Написание
этого набора вручную заняло бы недели и не дало бы выигрыша.

Оформление вводится на этапе 2 вместе с настоящими экранами. Этап 1 намеренно
обходится без библиотеки компонентов: его задача — доказать работоспособность
цепочки от браузера до политик изоляции в базе, и оформление этому не помогает.

**Тема зафиксирована светлой** и за системной настройкой не следует: сотрудники
сверяют экран с документами, которые печатаются на белом.

**Адаптивность** реализуется, но десктоп остаётся основным сценарием.

**Ошибки** формулируются на языке предметной области с указанием способа исправления
и ссылкой на проблемное поле. Технические коды пользователю не показываются.

## 7. Импорт

Основной канал — Excel/CSV, поскольку не требует доступа к системам заказчика.

Процесс: загрузка файла → автоматическое сопоставление колонок с полями, с ручной
правкой → пробный прогон → отчёт (сколько строк пройдёт, ошибки формата дат, дубли
по документу, записи без обязательных полей) → подтверждение → запись в рабочие таблицы.

Импорт идемпотентен по внешнему ключу: повторная загрузка того же файла обновляет
существующие записи, а не создаёт дубли. Частичный импорт с молчаливым пропуском строк
не допускается — либо применяются все строки, либо возвращается отчёт с номерами
проблемных.

## 8. Надёжность, безопасность, тестирование

**Персональные данные.** Размещение в РФ. Журнал доступа append-only: кто, когда и чью
карточку открывал или изменял. Шифрование соединений и резервных копий.

**Резервное копирование.** PostgreSQL в режиме PITR, ежемесячная проверка
восстановления. Непроверенная резервная копия резервной копией не считается.

**Тесты** сосредоточены там, где ошибка дорога:

- выделение номеров документов при конкурентных выдачах — номера уникальны и монотонны (пропуски допустимы);
- неизменяемость снимка выданного документа;
- изоляция арендаторов — отдельный набор, запрос под одним арендатором не видит строк другого;
- вычисление действующих условий договора на произвольную дату;
- идемпотентность импорта.

Интеграционные тесты выполняются на реальном PostgreSQL через testcontainers.
Сквозные тесты (Playwright): найти студента, выдать справку, добавить доп. соглашение.

**Наблюдаемость:** структурные логи (`slog`), метрики Prometheus, Sentry.
Распределённая трассировка не требуется, пока система остаётся монолитом.

**Эксплуатация:** `docker compose` на одном сервере в РФ. Миграции схемы — `goose`.
CI на GitHub Actions: линтер, тесты, сборка образа. Обновление без простоя
переключением между двумя репликами `api`. Kubernetes не применяется.

## 9. Этапы

Каждый этап завершается результатом, который можно показать конечному пользователю
и получить обратную связь. Каждый этап получает собственный план реализации.

| Этап | Содержание | Оценка |
|---|---|---|
| 0. Спайк | Шаблонизатор DOCX на реальном бланке: нормализация runs, подстановка, конвертация в PDF. Код выбрасывается, результат — ответ о применимости подхода. | 2–4 дня |
| 1. Скелет | Аутентификация, арендаторы, RLS, миграции, CI, деплой, HTTPS. Вертикальный срез через все слои. | ~2 недели |
| 2. Контингент | `person`/`enrollment`, история, поиск с опечатками, карточка студента, командная палитра. | ~3 недели |
| 3. Договоры | Договоры, доп. соглашения, вычисление условий на дату. | ~2 недели |
| 4. Документы | Шаблоны, сопоставление полей, предпросмотр, выдача с номером и снимком, PDF, QR-проверка. | ~3 недели |
| 5. Импорт | Сопоставление колонок, пробный прогон, отчёт об ошибках. | ~2 недели |
| 6. Пилот | Роли и права, журнал доступа, резервное копирование с проверкой, инструкция, внедрение у первого заказчика. | ~3 недели |

Суммарно до пилотного внедрения — около 15 недель сосредоточенной работы.

Дальнейшее развитие определяется обратной связью пилота. Вероятная очерёдность:
приказы и движение контингента, учебный процесс, личный кабинет студента, пакетная
выдача, ЭЦП, синхронизация через OData.

## 10. Принятые решения и их основания

| Решение | Основание |
|---|---|
| Модульный монолит вместо микросервисов | Целевая нагрузка не требует разделения; разделение утраивает срок до продукта и вводит распределённые транзакции внутри одного агрегата. |
| Собственный продукт вместо надстройки над 1С | Независимость от периметра и ИТ-службы заказчика; возможность продажи другим учебным заведениям. |
| Шаблоны в DOCX вместо HTML | Бланк утверждён в вузе и должен редактироваться сотрудником в Word; HTML-шаблоны потребовали бы разработчика на каждое изменение. |
